# Vendor Domain Alignment & Onboarding Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Bridge the Vendor domain gaps between frontend and backend by adding `category` and `taxId` directly into backend OpenAPI specs, database schema (`V1__initial_schema.sql`), and JPA entities, and implementing a high-fidelity "Onboard Vendor" modal in the frontend connected to `createVendor` API with optimistic local state fallback.

**Architecture:**
- **Backend Schema & OpenAPI**: Update `V1__initial_schema.sql` to add `category VARCHAR(255)` and `tax_id VARCHAR(50)` on `vendors` table. Update `VendorCreateRequest.yaml`, `VendorUpdateRequest.yaml`, and `VendorResponse.yaml` with `category` and `taxId`. Update `R__seed_test_data.sql` with realistic categories and tax IDs.
- **Backend Controller & Entity**: Add `category` and `taxId` to `VendorEntity` and map them in `VendorController` (`createVendor`, `updateVendor`, `toResponse`).
- **Frontend Contract & Adapters**: Update `frontend/src/types/vendor.ts` to include `category?: string` and `taxId?: string`. Update `vendorAdapter.ts` to cleanly round-trip `category` and `taxId` between backend DTOs and rich UI `Vendor` state.
- **Frontend Store & UI**: Add `addNewVendor(input: CreateVendorInput): Promise<Vendor>` to `useMasterData.ts` and `InvoiceContext.tsx`. Create `CreateVendorModal.tsx` and surface a `+ Onboard Vendor` button in `PropertyVendorMatching.tsx` (Active Mappings Directory tab).

**Tech Stack:** Spring Boot 4 / Java 21, PostgreSQL, OpenAPI Generator, React 19, TypeScript, Tailwind CSS, Lucide icons.

**Spec:** Option 1 (Full domain alignment: `category` & `taxId` persisted across backend & frontend).

---

## Global Constraints
- **Zero TypeScript Errors**: `npm --prefix frontend run build` must succeed after each task.
- **Zero Hardcoded UUIDs in Seed Data**: Primary keys in `R__seed_test_data.sql` must be generated by PostgreSQL's `gen_random_uuid()`.
- **Backward Compatibility**: `category` and `taxId` should be optional in `VendorCreateRequest` so existing tests or automated ingestion flows don't break.
- **No Stale Placeholders**: Clean `NULL` string handling in backend `VendorController` to prevent literal `"NULL"` values from polluting UI fields.

---

## Review Focus
1. **Category & Tax ID Round-tripping**: A vendor onboarded with custom category and tax ID must return those exact fields from the backend `/api/v1/vendors` and not revert to mock defaults.
2. **Payment Method Integrity**: Payment method options (`ACH`, `CHECK`, `CREDIT_CARD`) must align seamlessly between modal selection and backend enum without casing mismatches.
3. **Optimistic Store Update**: If backend is offline, `addNewVendor` must append a well-formed optimistic vendor to UI state with a generated ID and default category.
4. **Duplicate Payee Handling**: Modal validation must prevent empty vendor names and format phone numbers / tax IDs cleanly.
5. **Mapping Integration**: Newly onboarded vendor must immediately be available in the Payee selector inside Property-Vendor matching triage and active mappings.

```typescript
export interface CreateVendorInput {
  name: string;
  category: string;
  taxId: string;
  defaultPaymentMethod: PaymentMethod;
  phoneNumber?: string;
  paymentUrl?: string;
  remittanceAddress?: string;
}

export function toUIVendor(
  dto: VendorResponse,
  existingUIVendor?: UIVendor
): UIVendor {
  const cleanPhone =
    dto.phoneNumber && dto.phoneNumber !== 'NULL' ? dto.phoneNumber : undefined;
  const cleanUrl =
    dto.paymentUrl && dto.paymentUrl !== 'NULL' ? dto.paymentUrl : undefined;

  let uiStatus: 'verified' | 'unverified' | 'pending_review' = 'verified';
  if (existingUIVendor?.status) {
    uiStatus = existingUIVendor.status;
  } else if (dto.status === 'INACTIVE') {
    uiStatus = 'unverified';
  }

  return {
    id: dto.vendorUuid,
    name: dto.name,
    category: dto.category || existingUIVendor?.category || 'Commercial Facilities & Services',
    accountNumber:
      existingUIVendor?.accountNumber || `ACT-${dto.vendorUuid.slice(0, 6).toUpperCase()}`,
    defaultPaymentMethod: dto.paymentMethod,
    remittanceAddress:
      existingUIVendor?.remittanceAddress || 'PO Box 1000, Commercial Suite, US',
    taxId: dto.taxId || existingUIVendor?.taxId || 'XX-XXXXXXX',
    status: uiStatus,
    historicalMatchesCount: existingUIVendor?.historicalMatchesCount || 1,
    phoneNumber: cleanPhone,
    paymentUrl: cleanUrl,
  };
}

export function toBackendVendorCreate(
  ui: CreateVendorInput
): VendorCreateRequest {
  return {
    name: ui.name.trim(),
    category: ui.category.trim(),
    taxId: ui.taxId.trim(),
    phoneNumber: ui.phoneNumber?.trim() || undefined,
    paymentUrl: ui.paymentUrl?.trim() || undefined,
    paymentMethod: ui.defaultPaymentMethod,
    status: 'ACTIVE',
  };
}
```

- [ ] **Step 2: Add addNewVendor to useMasterData.ts**
```typescript
const addNewVendor = async (input: CreateVendorInput): Promise<Vendor> => {
  try {
    const created = await createUIVendor(input);
    setVendors((prev) => [created, ...prev]);
    return created;
  } catch {
    // Optimistic fallback for offline mode
    const fallback: Vendor = {
      id: `vend-local-${Date.now()}`,
      name: input.name,
      category: input.category,
      accountNumber: `ACT-${Math.floor(100000 + Math.random() * 900000)}`,
      defaultPaymentMethod: input.defaultPaymentMethod,
      remittanceAddress: input.remittanceAddress || 'PO Box 1000, Commercial Suite, US',
      taxId: input.taxId,
      status: 'verified',
      historicalMatchesCount: 0,
      phoneNumber: input.phoneNumber,
      paymentUrl: input.paymentUrl,
    };
    setVendors((prev) => [fallback, ...prev]);
    return fallback;
  }
};
```
