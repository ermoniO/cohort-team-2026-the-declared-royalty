# Frontend Architecture & Developer Guide

Welcome to the Invoice Automation Service frontend codebase! This guide outlines our team architectural conventions, coding patterns, and workflows to help all engineers write consistent, maintainable, and type-safe code.

---

## 1. Architectural Overview: The 4-Layer Pattern

Our frontend architecture follows a clear 4-layer separation of concerns:

```
src/
├── types/          ── Layer 1: Contracts & Domain Models
├── app/services/   ── Layer 2: API Client & Backend Communication
├── hooks/          ── Layer 3: Application State & Business Logic
└── components/     ── Layer 4: Presentation & User Interface
```

### Layer 1: `types/` (Data Contracts & Schemas)
- **`types/api.generated.ts`**: Auto-generated by `openapi-typescript` directly from the backend `openapi.yaml`. **Do not edit manually.**
- **`types/api.ts`**: Ergonomic aliases and utility helpers over the generated OpenAPI components (e.g., `PropertyResponse`, `VendorResponse`, `StripePaymentRequest`).
- **`types.ts`**: Rich UI view models used across React components (e.g., `Invoice`, `UIProperty`, `UIVendor`).

### Layer 2: `app/services/` (API Communication)
- **`apiClient.ts`**: Hybrid HTTP client combining `openapi-fetch` (strictly typed paths and parameters) and legacy methods (`get`, `post`, `put`, `delete`).
- Uses `import.meta.env.VITE_API_BASE_URL` with fallback to `http://localhost:8080`, allowing flexible port parameterization across branches.
- Domain services (`propertyService.ts`, `vendorService.ts`, `invoiceService.ts`, `paymentService.ts`, `auditLogService.ts`, `approvalMatrixService.ts`) encapsulate specific backend interactions.
- Legacy `features/**` directories re-export these services to ensure backward compatibility across the team.

```ts
// Example: Using openapi-fetch in a service
import { apiClient } from "./apiClient";
import type { PropertyResponse } from "@/types/api";

export async function getProperties(): Promise<PropertyResponse[]> {
  const { data, error } = await apiClient.GET("/api/v1/properties");
  if (error) throw new Error("Failed to fetch properties");
  return data ?? [];
}
```

### Layer 3: `hooks/` & `context/` (State & Business Logic)
- **`hooks/useInvoices.ts`**: Manages invoice collection state, approval workflows, exceptions, and live/mock disbursements.
- **`hooks/useMasterData.ts`**: Loads and manages master data (Properties, Vendors, GL Accounts, AP Seats).
- **`context/InvoiceContext.tsx`**: Context provider exposing state hooks across the entire component tree.
- Decouples UI rendering from backend fetching and policy execution.

### Layer 4: `components/` (Presentation & Interactions)
- Pure UI components styled with Tailwind CSS and Lucide icons.
- Consume state from `useInvoiceStore()` (via `InvoiceContext`).
- Responsible only for layout, form interactions, event triggers, and accessibility.

## 2. OpenAPI Generation Workflow

We use a schema-first contract approach. Whenever backend endpoints or OpenAPI schemas in `backend/src/main/resources/openapi/` change:

```bash
# In frontend/
npm run generate:api
```

This command runs `openapi-typescript` against `../backend/src/main/resources/openapi/openapi.yaml` and updates `frontend/src/types/api.generated.ts`.

> **Note**: `npm run build` runs `npm run generate:api` automatically as a `prebuild` hook to ensure contracts are always up to date before production bundling.

## 3. Dynamic Environment & Multi-Branch Setup

To avoid port collisions when working across multiple git branches or Docker worktrees simultaneously:

1. Copy `.env.example` to `.env`:
   ```bash
   cp .env.example .env
   ```
2. Configure your branch-specific ports:
   ```bash
   # Example: Secondary branch preset
   VITE_PORT=5175
   VITE_API_BASE_URL=http://localhost:8082
   ```
3. `apiClient` reads `VITE_API_BASE_URL` automatically, ensuring unit tests and the dev server talk to the right backend instance.

## 4. Testing & Verification

We use **Vitest** for unit tests. All test files live under `frontend/tests/`.

### Running Tests
```bash
# Run full unit test suite once
npm test

# Run tests in watch mode
npm run test:watch
```

### Writing Tests
Mock the global `fetch` using Vitest's `vi.stubGlobal`:
```ts
import { afterEach, beforeEach, describe, expect, it, vi } from "vitest";
import { getVendors } from "@/app/services/vendorService";

const fetchMock = vi.fn<typeof fetch>();

beforeEach(() => {
  vi.stubGlobal("fetch", fetchMock);
});

afterEach(() => {
  fetchMock.mockReset();
  vi.unstubAllGlobals();
});

describe("getVendors", () => {
  it("fetches vendor list successfully", async () => {
    fetchMock.mockResolvedValueOnce(
      new Response(JSON.stringify([{ vendorUuid: "123", name: "Acme" }]), { status: 200 })
    );

    const result = await getVendors();
    expect(result).toHaveLength(1);
    expect(result[0].name).toBe("Acme");
  });
});
```

### Production Build Check
Always run a full build before pushing code:
```bash
npm run build
```
This verifies TypeScript compilation, OpenAPI type synchronization, and Vite asset bundling.
