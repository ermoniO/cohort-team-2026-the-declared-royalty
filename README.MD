# Property Bill Automation System

A financial automation platform designed for property management portfolios to intake, parse, match, validate, approve, and execute payments for vendor invoices across multiple properties.

---

## Architecture & Technology Stack

* **Architecture Paradigm:** Monorepo, Contract-First (OpenAPI 3.0), Swagger for REST observability, Schema-First (Flyway) for DB Change management, PGAdmin for DB visualization.
* **Backend:** Java 21, Spring Boot 4.x, Spring Data JPA, Maven.
* **Frontend:** React + Vite (located under `/frontend`).
* **Database (Relational):** PostgreSQL 16 (financial ledger, state tracking, entity relations).
* **Storage (BLOB):** MinIO (S3-compatible storage for raw PDF invoices).
* **Payment Integration:** Stripe API (Test Mode).

## Local Environment Setup

### 1. Prerequisites
Ensure you have the following installed on your local machine:
*   [Node.js](https://nodejs.org) (v20+ or v22 recommended)
*   [Java 21](https://adoptium.net) (pinned via `.sdkmanrc`: run `sdk env install`)
*   [Docker Desktop](https://docker.com)
*   **Maven:** Use the included Maven wrapper (`backend/mvnw`). No system Maven installation is required.

### 2. Choose What Runs in Docker (Compose Profiles)

PostgreSQL, MinIO, and pgAdmin always start. The backend and frontend containers are opt-in through **Compose profiles**, set with `COMPOSE_PROFILES` (comma-separated) in your root `.env`:

```env
# Frontend: dev (hot reload) or prod (nginx build). Add "backend" to run it in Docker.
COMPOSE_PROFILES=dev,backend
```

| Profile | Service | Description |
| --- | --- | --- |
| `backend` | `backend` | Spring Boot API on `localhost:8080`. Leave it out to run the backend locally instead (see [Running the Backend](#running-the-backend)). |
| `dev` | `frontend-dev` | Vite dev server with hot reload on `localhost:5173`. `./frontend` is bind-mounted into the container. |
| `prod` | `frontend` | Production build served by nginx on `localhost:5173`. |

Common setups:

| `COMPOSE_PROFILES` | What runs in Docker |
| --- | --- |
| `dev,backend` | Everything, frontend with hot reload |
| `dev` | Infrastructure + frontend; backend runs from your IDE / `mvnw` |
| `prod,backend` | Full production-style stack |
| *(empty)* | Infrastructure only |

> `dev` and `prod` both use port `5173` (the backend's default CORS origin), so enable only one at a time.

To override `.env` for a single run, pass `--profile` flags (these replace the `.env` value, not add to it):

```bash
docker compose --profile prod --profile backend up -d --build
```

### 3. Start the Containers

From the repository root:

```bash
docker compose up -d --build

```

Verify services are running:

* **PostgreSQL:** `localhost:5432` (`database: invoice_automation_postgres`, `user: `, `password: `)
* **pgAdmin web console:** `http://localhost:5050` (`user: `, `password: `)
* **MinIO API:** `http://localhost:9000`
* **MinIO Web Console:** `http://localhost:9001` (User: ``, Password: ``)
* **Swagger Web Console:** `http://localhost:8080/swagger-ui`

## Database Migrations: Flyway

This project uses a **Schema-First** methodology via Flyway. The database schema in SQL is the primary source of truth for all storage rules and constraints; JPA entities strictly mirror the Flyway tables.

### File Naming Convention & Location

* **Location:** `backend/src/main/resources/db/migration/`
* Flyway Requires a Specific Location Path:** `src/main/resources/db/migration/`
* By standard convention in Spring Boot, Flyway scans the application classpath on startup specifically at `classpath:db/migration` looking for versioned scripts (`V1__...sql`, `V2__...sql`).
* To change the default** In `application.yml` (`spring.flyway.locations=classpath:custom/path`), but in 99% of professional Java/Spring projects, developers leave it at `src/main/resources/db/migration/` because every Spring developer, documentation tutorial, and CI/CD tool expects it there out of the box.
  *(Note: While path locations can technically be customized in `application.yml` via `spring.flyway.locations`, this project sticks strictly to the standard classpath default).*
* **Naming Pattern:** `V<Version>__<Description>.sql` (e.g., `V1__initial_schema.sql`, `V2__seed_test_data.sql`).
* Must start with a capital `V`.
* Must be followed by the version number.
* Must use **two consecutive underscores** (`__`).
* Must end in `.sql`.



### Applying Migrations

Flyway runs automatically whenever the Spring Boot service starts. To manually compile resources and execute pending migrations:

```bash
cd backend
./mvnw clean compile spring-boot:run

```

## API Contract & Code Generation: OpenAPI & Swagger

This project follows an **API Contract-First** development workflow. All endpoint interfaces and DTOs are defined in the modular OpenAPI specification located at `backend/src/main/resources/openapi/` and compiled directly into Java types for the backend.

### Modular Specification Layout

The contract is split into focused files using standard OpenAPI 3.0 `$ref` pointers:

*   **Root Contract:** `backend/src/main/resources/openapi/openapi.yaml` (contains `openapi`, `info`, `servers`, and top-level `$ref` references).
*   **Paths:** `backend/src/main/resources/openapi/paths/` (e.g., `properties.yaml`, `properties_by_id.yaml`, `users.yaml`, `vendors.yaml`).
*   **Schemas:** `backend/src/main/resources/openapi/components/schemas/` (one file per schema, e.g., `PropertyResponse.yaml`, `VendorResponse.yaml`).
*   **Parameters:** `backend/src/main/resources/openapi/components/parameters/` (reusable path/query parameters such as `VendorUuid.yaml`).

In `backend/pom.xml`, the `openapi-generator-maven-plugin` points to the root contract:
```xml
<inputSpec>${project.basedir}/src/main/resources/openapi/openapi.yaml</inputSpec>
```

> **Frontend Integration:** When generating TypeScript client types or SDKs, point your tooling to `backend/src/main/resources/openapi/openapi.yaml`.

### Adding an Endpoint or Schema

1. Create a path definition file in `backend/src/main/resources/openapi/paths/<resource>.yaml`.
2. Reference the file in `openapi.yaml` under `paths:`.
3. If new data structures are needed, create schemas in `backend/src/main/resources/openapi/components/schemas/<SchemaName>.yaml` and reference them under `components.schemas:` in `openapi.yaml`.
4. Run code generation:
   ```bash
   cd backend
   ./mvnw clean compile
   ```
   *Note: `openapi-generator-maven-plugin` is bound to the `generate-sources` phase and declared before `maven-compiler-plugin`, guaranteeing that generated DTOs and API interfaces are generated and added to compile roots before javac compiles the application code.*
5. Implement the generated interface in your controller (e.g., `public class PropertyController implements PropertiesApi`).

### Generating Java Interfaces and DTOs

1. Run the code generation plugin via Maven inside `backend/`:

```bash
cd backend
./mvnw clean compile
```

2. **Output Location:** Generated files are written to:
```text
backend/target/generated-sources/openapi/src/main/java/org/dsd/cohort2026fall/tdr/
├── api/          # Spring @RestController interfaces (e.g., PropertiesApi.java)
└── model/        # Request & Response DTOs (e.g., PropertyResponse.java)
```


4. **Implementation:** Hand-written controllers implement the generated interfaces (e.g., `public class PropertyController implements PropertiesApi`), ensuring compile-time safety without risking manual code overwrites during regeneration.

## Running the Backend

From the `backend/` directory:

```bash
./mvnw clean spring-boot:run

```

> When running the backend locally, leave `backend` out of `COMPOSE_PROFILES` so the container doesn't also bind port `8080`. The local process doesn't receive the environment compose sets, so provide `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `MINIO_ENDPOINT=localhost:9000`, `MINIO_USER`, and `MINIO_PASSWORD` (values from `.env`) in your IDE run configuration or shell.

### Stripe test mode

The Stripe integration is disabled by default. To enable the test-mode payment endpoint, add test credentials to the environment used by the backend:

```env
STRIPE_ENABLED=true
STRIPE_SECRET_KEY=sk_test_...
STRIPE_WEBHOOK_SECRET=whsec_...
STRIPE_CURRENCY=usd
```

The endpoint `POST /api/v1/invoices/{invoiceUuid}/stripe-payment` requires an `APPROVED` invoice, an `approvedAmount` that exactly matches the stored invoice amount, a Stripe test PaymentMethod ID, and `humanApprovalConfirmed: true`. The backend rejects the request until those conditions are met. Stripe webhook events are received at `POST /api/v1/stripe/webhook` and must include a valid `Stripe-Signature` header.

Use Stripe test keys and test PaymentMethods only. Live keys and real payment credentials are not supported by this integration phase.

From the root directory, you can run/redeploy the backend container only with (naming the service enables its profile automatically):

```bash
docker compose up -d --build backend
```

## Running the Frontend

**Locally (fastest hot reload):** from the `frontend/` directory, install dependencies and launch the development server:
```bash
npm install
npm run dev
```

**In Docker:** set `dev` (hot reload) or `prod` (nginx build) in `COMPOSE_PROFILES`, then from the root directory:
```bash
docker compose up -d --build
```

Either way the app is served at `http://localhost:5173`. The frontend calls the API at `http://localhost:8080` from your browser, so it works with the backend running either in Docker or locally.

> The `dev` container enables file-watch polling (`VITE_USE_POLLING=true`) because file change events don't propagate through Docker bind mounts on Windows/macOS. Plain `npm run dev` is unaffected.
